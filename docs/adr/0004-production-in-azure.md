# Production runs in Azure, not on-prem

**Status:** accepted

Production runs as a **second Azure environment**, not an on-prem VM. The POC first designed an on-prem topology (Linux telemetry VM exposing 443 + Power BI gateway on an existing IS Windows box) and reversed it before build: Ahmed pitched keeping production in Azure and **Karim Khalifa (Practice Manager, Data & AI) approved**. IS provisions an **empty resource group** in an ITWorx subscription and grants Ahmed **Contributor scoped to that RG** — that is IS's entire contribution. Ahmed deploys **all** resources himself via Bicep: the Postgres Flexible Server (**public endpoint**, `pg_cron` enabled), the Azure Container Apps environment + collector/sink Container App, and Log Analytics — then runs the schema-v2 migration over psql. This trades a ~$55–120/mo Azure bill for zero VM ops, no separate Power BI gateway machine (Power BI Service reaches Azure Postgres directly over the public endpoint), no IS provisioning of compute or database, and elastic in-place scaling — reusing the Bicep shape proven in the POC. Sizing/tiers were worked out in the POC's `docs/azure-production-sizing.md` (archived at `D:\projects\archive\cc-otel-azure`).

## Consequences

- **The Bicep is dual-target, both full-stack.** One set of parameters for the interim POC environment (VS-benefits subscription, `rg-cc-otel-poc`) and one for the production RG; **both create Postgres**, differing only in RG/subscription/sizing parameters. Postgres sizing (B2ms / 128 GB / 7-day PITR / `pg_cron`) stays in Bicep — there is no IS provisioning request to move it to.
- **Public endpoint is deliberate, not a default.** Because Ahmed owns the Postgres deploy, the Flexible Server is created with a **public endpoint** (firewall-restricted). This is what keeps the Power BI connection gateway-less — Power BI Service reaches it directly; a private-endpoint-only server would force a gateway VM back into scope, undoing a main reason for the Azure decision.
- **Marts refresh via `pg_cron` inside Postgres** (nightly, before the Power BI pull) — no VM cron host exists. Verified supported on Flexible Server (PG 16, `pg_cron` 1.6); requires `shared_preload_libraries` + `azure.extensions` + `cron.database_name=otel`, set by Ahmed's Bicep as server parameters at deploy time.
- **Cutover is POC-Azure → prod-Azure, in parallel**: the POC env rehearses the full prod stack, the proven stack is re-deployed to the prod RG, and the POC stays live as fallback until the adoption report refreshes green off production (see parallel cutover in CONTEXT.md). Pilot data is not migrated (ADR-0002).
- **Fallback if IS instead hands over connection strings only** (no RG Contributor): the deploy flow changes to IS running the container from a spec we provide. We plan for the Contributor model as the main line.
